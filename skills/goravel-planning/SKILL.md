# Goravel Planning

Produces a complete, reviewable implementation plan before any code is written. The goal is to surface every file that needs changing, every invariant to preserve, every ambiguity that needs a decision — so that implementation can proceed without surprises.

This skill is read-only. It explores the codebase, reads relevant files, and writes a plan. It does not edit or create source files.

## Workflow

Follow these steps in order. Do not start writing the plan until Steps 1–4 are complete.

### Step 1: Understand the Task

Extract from the user's message:

- **What** is being added or changed (new feature, new endpoint, refactor, bug fix, etc.)
- **Business rules** — constraints, invariants, edge cases, exclusions
- **Scope boundaries** — what components / modules / contexts this applies to (and what it explicitly does NOT apply to)
- **Ambiguities** — anything the description leaves unclear

### Step 2: Locate the Affected Code

Find the primary service, module, or package. Use the knowledge graph before reading files:

```
build_or_update_graph_tool({ repo_root })
query_graph_tool({ repo_root, pattern: "callers_of", target: "<symbol>" })
semantic_search_nodes_tool({ repo_root, query: "<key term>" })
```

Fall back to Grep/Glob/Read only when the graph does not cover the file or language. Identify the root of
the affected component and understand its layout (source files, tests, config, migrations).

### Step 3: Read Existing Patterns

Read the most relevant existing files to understand:

- **Schema / models** — data structures, naming conventions, existing values
- **Core logic** — existing predicates, helpers, dispatch patterns
- **Validation / guards** — how input is validated, what constraints are enforced
- **Configuration / build** — how the project is built, what tooling runs after changes
- **Tests** — how existing test suites are structured, what patterns look like

Read enough to know the exact code you will reference in the plan.

### Step 4: Identify All Touch Points

Build a complete list of every file that needs to change, organized by layer. For each file, note what specifically changes and why. Common layers to consider:

| Layer | Examples | What changes |
|---|---|---|
| Contracts / facades | `contracts/**`, `facades/**`, `app/facades/**` | New or changed method signatures, facade return types |
| Wiring | `foundation/`, `service_provider.go`, `bootstrap/app.go` | The new contract registered and bound |
| Migrations | `database/migrations/*.go` | Columns, indexes, table changes |
| Config | `config/*.go`, `.env.example` | New keys and their defaults |
| Validation | request `Validate(...)` rules, form requests | New rules and messages |
| Core logic | `app/**` service, command, controller | New functions, updated dispatch |
| Generated mocks | `app/mocks/**`, `mocks/**` | Regenerated by mockery |
| Tests | `*_test.go`, `tests/` | Cases that prove the change |
| Prompts / docs | `agents/**`, `skills/**`, `README.md` | Wording and contracts |

Adapt this to the actual project structure — discover the equivalent layers by reading the codebase.

### Step 5: Write the Plan

Output the plan in the format below. Be specific — include exact file paths, exact new identifiers, exact code snippets for non-trivial additions. The reader should be able to implement from the plan without opening the source files themselves. Inside each **File:** block, show the actual shape of the change — the new contract, the wiring, the package code, or the test.

```
## Open Questions

Things that must be confirmed before implementation. Plain words only — one short question per item, plus a small code example when the answer has a code shape:

1. <short question a non-expert can answer?> — <one sentence: what changes with each answer>
   <small code fence: before / after, or option A / option B — only if the answer has a code shape>
2. ...

(Omit this section if there are no genuine ambiguities.)
```

## How to write Open Questions

Open Questions are read by the person who asked for the change, not by the person
who writes the code. Write them so a non-expert can answer without opening the
source. This section is the full rule — the template above and the quality bar
below only point here.

For each question:

- Ask one short question in plain words — around 12 words is a good target, not a
  hard limit. Ask what you actually need to know, not "should we consider whether…".
- Add one plain sentence saying what changes with each answer, and why it matters.
- Add a small code fence showing the shape of the answer — before/after, or option A
  vs option B — only when the answer has a code shape. Show only the lines that
  differ, never a whole file. When the answer has no code shape at all (a package
  name, a doc sentence, the spelling of a config key), skip the fence and say so in
  one sentence instead.
- One decision per item. Never bundle two questions with "and".
- Keep the question sentence plain; put the real names — real field names, route
  paths, method names — inside the fence and in the sentence that explains the
  answers.
- In a real plan, never use `foo`, `...`, or `TBD`. The template above is the one
  exception — its placeholders are there to be replaced.
- Avoid "utilize", "leverage", "aforementioned", "hereby", "consider whether".

Example output:

1. Should a wrong password return 401 or 403? — 401 means "wrong login", 403 means
   "right login but blocked". The app returns the login screen on 401 and the
   support link on 403, so the frontend needs the code to tell the two apart.

   ```go
   // if 401: wrong login
   return ctx.Response().Json(401, http.Json{"error": "email or password is incorrect"})

   // if 403: login is right but the account is blocked — same message on purpose
   return ctx.Response().Json(403, http.Json{"error": "email or password is incorrect"})
   ```

2. Should two accounts be able to share one email? — No adds a unique index, so the
   second signup fails; yes lets both accounts exist.

   ```go
   // if no (unique)
   table.String("email")
   table.Unique("email")

   // if yes (not unique)
   table.String("email")
   ```

## What counts as real user code

Use `Real user code` to show code a Goravel application author would actually
write in a real app, not internal framework implementation.

Prefer patterns from `goravel/goravel` and `goravel/example`, such as:

- route registration
- middleware usage
- controller code
- request validation
- ORM queries
- auth flows

Example:

```go
facades.Route().Middleware(middleware.Jwt()).Get("users", userController.Index)
```

## Quality Bar for the Plan

Before outputting, verify:

- Every file that needs changing is listed — no layer silently left out
- File paths are exact (verified by the searches in Steps 2–3)
- Code snippets use the correct identifiers (function names, type names, constant names) as they actually exist in the codebase, not guesses
- The sequence respects actual build and dependency order for this project
- Open Questions are genuine ambiguities, not things that can be determined by reading the code
- Every Open Question follows `How to write Open Questions` above — one short plain-words question, a plain sentence on what each answer changes, and a code example only where the answer has a code shape
- The plan describes the change and shows its code shape; it never edits a file.
- If the work affects user-facing behavior, include `Real User Code Example`. 
- If the work is entirely internal, say that explicitly and omit the user code example only when no realistic user-facing snippet exists.
- Never use pseudo-code placeholders inside code fences. Use realistic Goravel code patterns.
